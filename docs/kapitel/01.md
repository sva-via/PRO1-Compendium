# Kapitel 1 – Hvad er et objekt?

## 1\. Introduktion

Dette kapitel handler om det mest grundlæggende spørgsmål i objektorienteret programmering: **Hvad er et objekt?**

I PRO1 er målet ikke først og fremmest at lære Java som sprog, men at lære at **modellere virkeligheden i software**.

Et objekt er ikke blot en teknisk konstruktion – det er en model af et begreb fra et domæne.

Vi begynder derfor ikke med syntaks, men med forståelse:

* Hvad er forskellen på en variabel og et objekt?
* Hvad betyder det, at en klasse modellerer et begreb?
* Hvad er state og adfærd?
* Hvilke regler gælder for et objekt?

\---

## 2\. Objekt vs. variabel

En variabel er et sted i programmet, hvor vi gemmer en værdi.

```java
double celsius = 20.2;
```

Her gemmer variablen `celsius` tallet 20.2

Men en variabel er ikke et begreb. Den er kun en teknisk måde at referere til en værdi på.

Et objekt derimod repræsenterer noget med:

* en tilstand (state)
* en adfærd (metoder)
* et ansvar

```java
Temperature t1 = new Temperature(20.2);
```

* `t1` er en variabel (en reference)
* objektet er instansen af `Temperature`

Variablen bruges til at arbejde med objektet – men det er objektet, der repræsenterer begrebet.

\---

## 3\. Klassen som model af et begreb

En klasse beskriver, hvordan objekter af en bestemt type ser ud og opfører sig.

```java
public class Temperature
{
  private double celsius;

  public Temperature(double celsius)
  {
    this.celsius = celsius;
  }

  public double getCelsius()
  {
    return celsius;
  }

  public double getKelvin()
  {
    return celsius + 273.15;
  }
}
```

Klassen modellerer begrebet temperatur.

Den:

* indeholder data (state)
* definerer adfærd (metoder)
* afgrænser sit ansvar

\---

## 4\. State og adfærd

**State** er de data, objektet indeholder.  
**Adfærd** er det, objektet kan gøre.

Eksempel:

State:

```java
private double celsius;
```

Adfærd:

```java
public double getCelsius()
{
  return celsius;
}

public double getKelvin()
{
  return celsius + 273.15;
}
```

Adfærd bør altid være relateret til objektets begreb.

\---

## 5\. Hvad er en invariant?

En invariant er en regel om objektets tilstand, som **altid skal være opfyldt**:

* efter konstruktion
* efter enhver offentlig metode

Det er det, der altid skal være sandt for objektet.

For `Temperature` gælder fx:

Temperaturen må aldrig være under det absolutte nulpunkt (-273.15 °C).

Objektet skal beskytte sig selv mod ugyldig tilstand.

\---

## 6\. Beskyttelse af invarianten

Vi sikrer invarianten i konstruktøren:

```java
public class Temperature
{
  private double celsius;

  public Temperature(double celsius)
  {
    if (celsius < -273.15)
    {
      throw new IllegalArgumentException("Below absolute zero");
    }
    this.celsius = celsius;
  }

  public double getCelsius()
  {
    return celsius;
  }
}
```

Her bruges `IllegalArgumentException` til at afvise input, der bryder invarianten.

Det er ikke en fejl i programmet – det er en beskyttelse af objektets gyldighed.

\---

## 7\. Designovervejelser

Hvorfor lave en klasse?

* Samler relaterede data
* Giver begrebet identitet
* Kontrollerer korrekt brug
* Beskytter sin egen tilstand

Alternativet med løse variabler giver:

* ingen samlet struktur
* ingen ansvarlighed
* ingen garanti for gyldighed

\---

## 8\. Typiske fejl og misforståelser

1. At tro at objekt = variabel
2. At placere adfærd uden for objektet
3. At lade klassen gøre for meget
4. At ignorere ugyldige tilstande

Et objekt bør repræsentere ét begreb med klart ansvar.

\---

## 9\. Testidéer

Når vi designer en klasse, bør vi tænke:

* Hvad er gyldige input?
* Hvad er grænsetilfælde?
* Hvad er ugyldigt?

Eksempel (Temperature):

* Normal: 20 → OK
* Grænse: -273.15 → OK
* Ugyldigt: -273.14 → skal afvises

Disse overvejelser danner grundlag for tests.

## Afslutning

Et objekt er ikke blot en datastruktur.

Det er:

* en model af et begreb
* en samling af state
* en enhed med ansvar
* en aktør med adfærd
* en struktur med regler (invariant)

At programmere objektorienteret betyder derfor ikke primært at skrive metoder.

Det betyder at træffe designbeslutninger om:

* Hvilke begreber findes i domænet?
* Hvad er deres ansvar?
* Hvilke regler skal de overholde?
* Hvordan skal de samarbejde?

Resten af kurset bygger på denne forståelse.
