## 2. Inheritance Models "Is-A"

Inheritance represents:

> is-a

Examples:

```text
Car is a Vehicle
```

```text
Van is a Car
```

```text
SportsCar is a Car
```

```text
Shape is a Circle
```

Good inheritance:

```text
Vehicle
├── Bicycle
├── Car
│   ├── Van
│   └── SportsCar
```

Poor inheritance:

```text
Car → Engine
```

An engine is not a car.

That is:

```text
has-a
```

not:

```text
is-a
```

Inheritance should only model specialization. :contentReference[oaicite:0]{index=0}

## 3. Responsibility in Inheritance

Superclass:

```text
General responsibility
```

Subclass:

```text
Specialized responsibility
```

Example:

Vehicle responsibility:

- owner
- price

Car responsibility:

- registration number

Van responsibility:

- max load

SportsCar responsibility:

- max speed

General responsibility belongs higher.

Specialized responsibility belongs lower. :contentReference[oaicite:1]{index=1}

## 4. Avoiding Duplication

Without inheritance:

```text
Car
- owner
- price
- regNo

Van
- owner
- price
- regNo
- maxLoad
```

Notice duplication:

- owner
- price

Better:

```text
Vehicle
- owner
- price

Car
- regNo

Van
- maxLoad
```

Inheritance reduces duplication.

Advantages:

- simpler maintenance
- less repeated code
- clearer design

Inheritance should simplify systems. :contentReference[oaicite:2]{index=2}

## 5. Constructor Responsibility

Superclass establishes superclass state.

Example:

```java
public class Vehicle
{
  private String owner;

  public Vehicle(String owner)
  {
    this.owner = owner;
  }
}
```

Subclass establishes subclass state.

Example:

```java
public class Car extends Vehicle
{
  private String regNo;

  public Car(String owner,
             String regNo)
  {
    super(owner);

    this.regNo = regNo;
  }
}
```

Vehicle establishes:

- owner

Car establishes:

- regNo

Responsibility remains separated. :contentReference[oaicite:3]{index=3}

## 6. The super Constructor Call

Example:

```java
super(owner);
```

Meaning:

> Let the superclass establish superclass state.

The subclass should not duplicate superclass fields.

Wrong:

```java
public class Car extends Vehicle
{
  private String owner;
}
```

The owner already exists in Vehicle.

Duplicating superclass data creates poor design. :contentReference[oaicite:4]{index=4}

## 7. Overriding Methods

Subclasses may extend inherited behavior.

Example:

Vehicle:

```java
public String toString()
{
  return "Owner=" + owner;
}
```

Car:

```java
public String toString()
{
  return super.toString()
       + ", regNo=" + regNo;
}
```

The subclass builds on superclass behavior.

This avoids duplication. :contentReference[oaicite:5]{index=5}

---

## 8. Calling Superclass Methods

Example:

```java
super.toString()
```

Meaning:

> Use superclass implementation first.

Then add subclass information.

Example:

Vehicle:

```text
Owner=Bob
```

Car:

```text
Owner=Bob,
regNo=BZ41377
```

Superclass behavior should often be reused. :contentReference[oaicite:6]{index=6}

## 9. Designing equals

Superclass equality:

```java
public boolean equals(
    Object obj)
{
  if (obj == null)
  {
    return false;
  }

  Vehicle other =
      (Vehicle)obj;

  return owner.equals(
             other.owner);
}
```

Subclass equality:

```java
public boolean equals(
    Object obj)
{
  Car other =
      (Car)obj;

  return super.equals(obj)
      && regNo.equals(
             other.regNo);
}
```

Superclass compares:

- superclass state

Subclass compares:

- subclass state

Equality remains layered. :contentReference[oaicite:7]{index=7}

## 10. Abstract or Not?

Some classes are too general.

Question:

Should this exist?

```java
new Vehicle("Bob")
```

Sometimes:

> No

Examples that may be abstract:

```text
Vehicle
Shape
Animal
```

Examples:

```text
Shape
├── Circle
└── Rectangle
```

```text
Animal
├── Lion
└── Elephant
```

Abstract classes model concepts that are incomplete or too general. :contentReference[oaicite:8]{index=8}

## 11. Why Use Abstract Classes?

Two common reasons:

### Incomplete class

Example:

```java
public abstract double
getArea();
```

No implementation exists.

Subclasses must provide it.

---

### Too general

Example:

```text
Vehicle
```

A general concept should sometimes prevent object creation.

Abstract prevents:

```java
new Vehicle(...)
```

from compiling. :contentReference[oaicite:9]{index=9}

## 12. Encapsulation in Inheritance

Example:

```java
private String owner;
```

Private fields:

- protect object state
- preserve invariants

Alternative:

```java
protected String owner;
```

Protected allows direct subclass access.

Course recommendation:

Prefer:

```java
private
```

Use methods:

```java
getOwner()
```

Encapsulation remains important even with inheritance. :contentReference[oaicite:10]{index=10}

---

## 13. Prefer Encapsulation

Good:

```java
super.toString()
```

Good:

```java
getOwner()
```

Less good:

```java
protected owner
```

Direct field access increases coupling.

Encapsulation protects valid state.

Good design remains important. :contentReference[oaicite:11]{index=11}

## 14. Testing Inheritance

Inheritance behavior should be tested.

Example:

```java
@Test void testToString()
{
  Vehicle car =
      new Car(
          "Bob",
          125000,
          "BZ41377");

  assertEquals(
      "Owner=Bob, "
    + "price=125000.0, "
    + "regNo=BZ41377",
      car.toString());
}
```

Tests should verify:

- constructor behavior
- inherited behavior
- overridden methods
- abstract subclasses

Testing remains important. :contentReference[oaicite:12]{index=12}

5. Making everything abstract
6. Using protected unnecessarily
7. Breaking encapsulation
