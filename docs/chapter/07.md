# Kapitel 7 – Fra specifikation til tests

## 1. Introduktion

Nu tager vi næste skridt:

👉 Hvordan går vi fra en **beskrivelse af en klasse** til **konkrete tests**?

Dette er centralt, fordi:

- vi ofte får krav som tekst
- vi skal kunne omsætte dem til kode
- vi senere vil kunne bruge værktøjer som Spec2JUnit

---

## 2. Hvad er en specifikation?

En specifikation beskriver:

- hvad en klasse skal gøre
- hvilke regler der gælder
- hvilke input der er gyldige/ugyldige

Eksempel:

> En Name-klasse skal repræsentere et navn med fornavn og efternavn.  
> Ingen af delene må være tomme eller null.  
> Metoden getFullName returnerer "fornavn efternavn".

---

## 3. Trin 1: Find regler

Læs specifikationen og identificér:

- gyldige situationer
- ugyldige situationer
- forventet adfærd

Eksempel:

Regler:
- firstName ≠ null
- firstName ≠ ""
- lastName ≠ null
- lastName ≠ ""
- getFullName → korrekt sammensætning

---

## 4. Trin 2: Lav testidéer

Omsæt reglerne til konkrete cases:

- ("Ada", "Lovelace") → "Ada Lovelace"
- ("A", "L") → "A L"
- ("", "Lovelace") → exception
- (null, "Lovelace") → exception

👉 Dette er broen mellem tekst og test.

---

## 5. Trin 3: Skriv tests

```java
@Test
void getFullName_normalCase()
{
  Name name = new Name("Ada", "Lovelace");
  assertEquals("Ada Lovelace", name.getFullName());
}

@Test
void konstruktør_kasterException_vedTomtFornavn()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Name("", "Lovelace"));
}
```

---

## 6. Mønster

Vi kan opsummere processen:

1. Læs specifikation  
2. Find regler  
3. Lav testidéer  
4. Skriv tests  

---

## 7. Typiske fejl

1. At springe direkte til kode  
2. At overse ugyldige input  
3. At misforstå krav  
4. At skrive for få tests  

---

## 8. Designprincip

> Tests er en konkret fortolkning af specifikationen.

Hvis testen er forkert → er forståelsen forkert.

---

## 9. Refleksionsspørgsmål

1. Hvad er forskellen på specifikation og implementering?  
2. Hvorfor er testidéer et vigtigt mellemtrin?  
3. Hvordan ved vi, om vi har forstået kravene korrekt?  
4. Hvad sker der, hvis vi tester det forkerte?

## 11. Frem mod Spec2JUnit

Vi kan nu:

- læse en specifikation
- finde regler
- formulere testcases

👉 Det betyder, at vi er klar til at bruge værktøjer som GPT til at hjælpe med at generere tests.

Men:

> Vi skal altid kunne vurdere, om output er korrekt.
