# Chapter 6 – Responsibility and Encapsulation

## 1. Introduction

Session 6 focuses on one of the central ideas in object-oriented programming:

> Objects should be responsible for their own data and behavior.

The focus is on:

- encapsulation
- responsibility
- placing logic correctly
- static methods
- `LocalDate`
- exception handling with `try-catch`

The goal is to design classes that are readable, maintainable, and responsible for their own behavior.

---

## 2. Responsibility in Object-Oriented Design

An object should be responsible for operations related to its own data.

Example:

Less good:

```java
person.getAge() >= 18
```

Better:

```java
person.isAdult()
```

The object itself should decide whether it represents an adult.

This improves:

- readability
- encapsulation
- maintainability

---

## 3. Encapsulation

Encapsulation means:

- protecting internal data
- controlling access to state
- providing meaningful operations

Instead of exposing raw data, objects should provide behavior.

Example:

Less good:

```java
student.getEmail() != null
```

Better:

```java
student.hasEmail()
```

The object hides internal details and provides meaningful operations.

---

## 4. Avoid Working Directly on Object Data

Good object-oriented design avoids taking data out of objects to work with it externally.

Less good:

```java
email1.getDomain().equals(email2.getDomain())
```

Better:

```java
email1.sameDomainAs(email2)
```

The logic belongs inside the responsible class.

---

## 5. Benefits of Proper Responsibility

Placing responsibility correctly provides several advantages.

### Better Readability

Example:

```java
person.isAdult()
```

is easier to understand than:

```java
person.getAge() >= 18
```

### Less Coupling

Other classes do not need to know internal details.

### Easier Maintenance

If the logic changes, only one class must be updated.

---

## 6. Repeated Logic Is a Warning Sign

Repeated logic often indicates poor responsibility placement.

Example:

```java
if (email.getDomain().equals("dk"))
```

appearing in many places is problematic.

Instead:

```java
email.isDanishDomain()
```

The object should contain the logic related to itself.

---

## 7. Calculated Data vs Stored Data

Sometimes data should not be stored directly.

Example:

Less good:

```java
private int age;
```

Better:

```java
private LocalDate birthDate;
```

Age changes over time.

Birth date is stable and can be used to calculate age.

This is an important design decision.

---

## 8. LocalDate

`LocalDate` represents dates.

Example:

```java
LocalDate birthday = LocalDate.of(2000, 10, 25);
```

`LocalDate` provides useful methods.

Example:

```java
birthday.isAfter(LocalDate.now())
```

Session 6 introduces `LocalDate` as a better way to model dates.

---

## 9. Validating Dates

Dates must also follow invariants.

Example:

```java
if (birthDate.isAfter(LocalDate.now()))
{
  throw new IllegalArgumentException(
      "Birth date cannot be in the future");
}
```

The object should reject impossible dates.

---

## 10. Static Methods

A static method belongs to the class itself rather than to an object.

Example:

```java
private static LocalDate convertToDate(
    int day,
    int month,
    int year)
{
  return LocalDate.of(year, month, day);
}
```

Static methods are useful when:

- the method does not depend on object state
- the method is a helper method

---

## 11. Helper Methods

Helper methods simplify complex logic.

Example:

```java
private static LocalDate convertToDate(
    int day,
    int month,
    int year)
{
  // conversion logic
}
```

Advantages:

- improves readability
- avoids duplicated code
- separates responsibilities

---

## 12. Constructor Delegation

Constructors can delegate to other constructors.

Example:

```java
public Person(String name, int day, int month, int year)
{
  this(name, convertToDate(day, month, year));
}
```

Advantages:

- avoids duplicated validation
- centralizes initialization
- improves consistency

---

## 13. Exception Handling with try-catch

Some operations may throw exceptions.

`try-catch` allows exceptions to be handled.

Example:

```java
try
{
  return LocalDate.of(year, month, day);
}
catch (DateTimeException e)
{
  throw new IllegalArgumentException(
      "Illegal date", e);
}
```

The program attempts an operation in the `try` block.

If an exception occurs, the `catch` block handles it.

---

## 14. Wrapping Exceptions

Sometimes low-level exceptions are converted into more meaningful exceptions.

Example:

```java
catch (DateTimeException e)
{
  throw new IllegalArgumentException(
      "Illegal date", e);
}
```

The class provides a clearer domain-related message.

---

## 15. Testing Exceptions

Exception handling should also be tested.

Example:

```java
@Test void constructorRejectsIllegalDate()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Person("Lars", 31, 2, 2000));
}
```

Tests should verify:

- valid behavior
- invalid behavior
- correct exceptions

---

## 16. Good Design Principles from Session 6

### Ask the Object

Prefer:

```java
person.isAdult()
```

instead of:

```java
person.getAge() >= 18
```

### Avoid Duplicated Logic

Place logic in one responsible class.

### Protect Object State

Objects should maintain valid state internally.

### Store Stable Data

Prefer stable data such as `birthDate` over calculated values such as `age`.

---

## 17. Typical Beginner Mistakes

Common mistakes:

1. Placing logic outside the responsible object
2. Exposing too much internal data
3. Duplicating logic
4. Storing calculated data unnecessarily
5. Writing static methods that should be instance methods
6. Ignoring exceptions
7. Catching exceptions without handling them properly

## Summary

Session 6 focuses on responsibility and encapsulation.

Important ideas include:

- objects should manage their own behavior
- logic belongs inside the responsible class
- encapsulation protects object state
- repeated logic should be avoided
- stable data is often better than calculated data
- static helper methods can simplify design
- `LocalDate` improves date handling
- `try-catch` handles exceptional situations

Good object-oriented design is largely about assigning responsibility correctly.
