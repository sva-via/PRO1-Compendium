# Kapitel 6 – Systematisk testdesign

## 1. Introduktion

Indtil nu har vi skrevet enkelte tests.

Nu tager vi næste skridt:

👉 Hvordan tester vi **systematisk**?

Målet er ikke bare at teste noget – men at teste rigtigt.

---

## 2. Hvorfor systematisk test?

Hvis vi kun tester “tilfældigt”, risikerer vi:

- at overse fejl
- at tro noget virker, selvom det ikke gør
- at få uforudsigelig adfærd

Systematisk test betyder:

> Vi tænker over, hvilke situationer der findes – før vi skriver testen.

---

## 3. AAA-strukturen

En test følger typisk tre trin:

**Arrange**
- opret objekter
- gør klar

**Act**
- kald metoden

**Assert**
- tjek resultatet

Eksempel:

```java
@Test
void getFullName_returnsCorrectName()
{
  // Arrange
  Name name = new Name("Ada", "Lovelace");

  // Act
  String result = name.getFullName();

  // Assert
  assertEquals("Ada Lovelace", result);
}
```

---

## 4. Tre typer testcases

Når vi designer tests, bør vi altid tænke i tre typer:

### 1. Normale tilfælde
Det mest almindelige brug

- "Ada", "Lovelace"

---

### 2. Grænsetilfælde
Situationer tæt på grænser

- ét bogstav
- meget lange navne

---

### 3. Ugyldige input
Input der skal afvises

- null
- tom streng

---

## 5. Eksempel: Name

Vi kan systematisere vores tests:

### Normal test

```java
@Test
void getFullName_normalCase()
{
  Name name = new Name("Ada", "Lovelace");
  assertEquals("Ada Lovelace", name.getFullName());
}
```

---

### Grænsetilfælde

```java
@Test
void getFullName_singleLetters()
{
  Name name = new Name("A", "L");
  assertEquals("A L", name.getFullName());
}
```

---

### Ugyldigt input

```java
@Test
void konstruktør_kasterException_vedNull()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Name(null, "Lovelace"));
}
```

---

## 6. Hvad skal testes?

En god tommelfingerregel:

Test:

- konstruktøren (gyldige og ugyldige input)
- metoder (normal og grænsetilfælde)
- mutatorer (ændringer + fejl)
- exception

---

## 7. Testidéer før kode

Før du skriver tests, bør du lave en liste:

Eksempel:

Name:

- ("Ada", "Lovelace") → OK
- ("A", "L") → OK
- ("", "Lovelace") → exception
- (null, "Lovelace") → exception

👉 Dette er testdesign.

---

## 8. Designprincip

> Gode tests kommer fra god forståelse af problemet.

Ikke fra at skrive kode hurtigt.

---

## 9. Typiske fejl

1. Kun at teste normale tilfælde  
2. Ikke at teste exception  
3. At skrive tests uden plan  
4. At teste for lidt  

---

## 10. Refleksionsspørgsmål

1. Hvad er forskellen på normale tilfælde og grænsetilfælde?  
2. Hvorfor er ugyldige input vigtige at teste?  
3. Hvad sker der, hvis vi ikke tester systematisk?  
4. Hvordan ved vi, om vi har testet nok?

---

## Afslutning

Vi har nu introduceret systematisk testdesign:

- AAA-struktur
- tre typer testcases
- testidéer før kode

Dette er et vigtigt skridt:

👉 Det er denne måde at tænke på, der gør det muligt senere at:
- læse en specifikation
- udlede testcases
- bruge værktøjer som Spec2JUnit kritisk og korrekt
