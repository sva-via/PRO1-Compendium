# Chapter 5 – Invariants

## 1. Introduction

Session 5 introduces one of the most important ideas in object-oriented design:

> An object must always remain valid.

The focus is on:

- invariants
- validation
- constructor responsibility
- setter responsibility
- exceptions
- immutable and mutable objects

The goal is to design classes that protect themselves against illegal state.

---

## 2. What Is an Invariant?

An invariant is a rule that must always be true for an object.

Examples:

### Temperature

A temperature cannot be below absolute zero.

```text
celsius >= -273.15
```

### Rectangle

A rectangle must have positive dimensions.

```text
length > 0
width > 0
```

### Student

```text
name cannot be null or blank
semester must be between 1 and 10
email must either be null (to indicate no email given) or have a valid format
```

An object that violates its invariants is invalid.

---

## 3. Constructors Must Establish Valid State

A constructor is responsible for creating valid objects.

Example:

```java
public Temperature(double celsius)
{
  if (celsius < -273.15)
  {
    throw new IllegalArgumentException(
        "Temperature cannot be below absolute zero.");
  }

  this.celsius = celsius;
}
```

The constructor checks the input before assigning values.

If the input is invalid, the object should not be created.

---

## 4. IllegalArgumentException

`IllegalArgumentException` is used when a method receives illegal input.

Example:

```java
throw new IllegalArgumentException(
    "Temperature cannot be below absolute zero.");
```

This immediately stops the constructor or method.

After Session 5, invalid input should normally cause an `IllegalArgumentException`.

---

## 5. Testing Exceptions

JUnit can test that exceptions are thrown.

Example:

```java
@Test void temperatureBelowAbsoluteZero()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Temperature(-273.16));
}
```

Exception tests are important because invalid input must also be tested.

---

## 6. Validation in Constructors

Validation means checking whether input values are legal.

Example:

```java
public Rectangle(double length, double width)
{
  if (length <= 0 || width <= 0)
  {
    throw new IllegalArgumentException(
        "length and width have to be positive");
  }

  this.length = length;
  this.width = width;
}
```

Validation protects the object's invariants.

---

## 7. Multiple Invariants

Classes often have several invariants.

Example:

```java
public Student(String name, int semester, String email)
{
  if (name == null || name.isBlank())
  {
    throw new IllegalArgumentException(
        "Name cannot be null or blank");
  }

  if (semester < 1 || semester > 10)
  {
    throw new IllegalArgumentException(
        "Semester must be between 1 and 10");
  }

  if (email != null &&
      (!email.contains("@") || !email.contains(".")))
  {
    throw new IllegalArgumentException(
        "Wrong email format: " + email);
  }

  this.name = name;
  this.semester = semester;
  this.email = email;
}
```

Each invariant protects part of the object's state.

---

## 8. Setters Must Preserve Invariants

Constructors establish valid state.

Setter methods must preserve valid state.

Example:

```java
public void setSemester(int semester)
{
  if (semester < 1 || semester > 10)
  {
    throw new IllegalArgumentException(
        "Semester must be between 1 and 10");
  }

  this.semester = semester;
}
```

An object must remain valid after every method call.

---

## 9. Avoiding Duplicated Validation

Validation logic should not be duplicated.

Bad design:

```java
public Student(String name, int semester, String email)
{
  // validation here
}

public void setSemester(int semester)
{
  // same validation again
}
```

Better design:

```java
public Student(String name, int semester, String email)
{
  this.name = name;
  setSemester(semester);
  setEmail(email);
}
```

The constructor reuses the setter logic.

Advantages:

- less duplicated code
- easier maintenance
- more consistent validation

---

## 10. Constructor Delegation

Constructors can delegate to other constructors.

Example:

```java
public Student(String name)
{
  this(name, 1, null);
}
```

Advantages:

- avoids duplicated initialization logic
- ensures consistent validation
- improves readability

---

## 11. Mutable and Immutable Objects

### Mutable Objects

A mutable object can change state after creation.

Example:

```java
student.setSemester(3);
```

### Immutable Objects

An immutable object cannot change after creation.

Example idea:

```java
String
```

Immutable objects are often easier to reason about because their state never changes.

---

## 12. Validation and Responsibility

Validation belongs inside the object.

Good:

```java
Student s = new Student("Bob", 3, "bob@builder.dk");
```

Bad:

```java
if (s.getSemester() >= 1 && s.getSemester() <= 10)
{
  // external validation
}
```

The object should protect itself.

This is part of encapsulation and responsibility.

---

## 13. Boundary Values

Boundary values are especially important in validation.

Example:

```text
semester = 1   valid
semester = 10  valid
semester = 0   invalid
semester = 11  invalid
```

Tests should include:

- valid values
- invalid values
- boundary values 

---

## 14. Testing Invariants

Tests should verify both:

- legal state
- illegal state

Example:

```java
@Test void validSemester()
{
  Student s = new Student("Bob", 3, null);

  assertEquals(3, s.getSemester());
}
```

Example:

```java
@Test void invalidSemesterThrowsException()
{
  assertThrows(IllegalArgumentException.class,
      () -> new Student("Bob", 11, null));
}
```

---

## 15. Typical Beginner Mistakes

Common mistakes:

1. Forgetting validation
2. Allowing invalid state
3. Duplicating validation logic
4. Validating outside the class
5. Writing setters that break invariants
6. Forgetting boundary cases
7. Creating partially initialized objects

## Summary

Session 5 focuses on protecting object validity.

Important ideas include:

- invariants describe valid state
- constructors establish invariants
- setters preserve invariants
- invalid input should throw exceptions
- validation belongs inside the object
- duplicated validation should be avoided
- mutable objects require careful protection

Good object-oriented design means creating objects that always remain valid.
