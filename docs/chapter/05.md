# Kapitel 5 – Ændring af tilstand (mutatorer)

## 1. Introduktion

Indtil nu har vores objekter været **uænderlige** efter oprettelse.

Men i mange modeller skal et objekt kunne ændre sin tilstand.

👉 Det gør vi med metoder, der ændrer state – kaldet **mutatorer**.

---

## 2. Eksempel: udvidelse af Name

Vi tilføjer en metode, der kan ændre efternavn:

```java
public void setLastName(String lastName)
{
  this.lastName = lastName;
}
```

Nu kan vi skrive:

```java
Name name = new Name("Ada", "Lovelace");
name.setLastName("Byron");
```

---

## 3. Problemet

Denne metode tillader:

```java
name.setLastName("");
name.setLastName(null);
```

👉 Vi kan nu bryde klassens invariant.

---

## 4. Regel

> Enhver metode skal bevare objektets invariant.

Det gælder ikke kun konstruktøren – men alle metoder.

---

## 5. Korrekt løsning

Vi tilføjer validering:

```java
public void setLastName(String lastName)
{
  if (lastName == null || lastName.isBlank())
  {
    throw new IllegalArgumentException("Last name cannot be empty");
  }
  this.lastName = lastName;
}
```

---

## 6. Designovervejelse: skal vi overhovedet have mutatorer?

Spørg:

- Giver det mening, at objektet ændrer sig?
- Skal objektet være uændeligt (immutable)?

Eksempel:
- Name → ofte uændeligt
- BankAccount → ændrer sig

👉 Valget er en designbeslutning.

---

## 7. Test af mutatorer

```java
@Test
void setLastName_changesLastName()
{
  Name name = new Name("Ada", "Lovelace");
  name.setLastName("Byron");
  assertEquals("Ada Byron", name.getFullName());
}
```

---

## 8. Test af exception

```java
@Test
void setLastName_kasterException_vedTomtNavn()
{
  Name name = new Name("Ada", "Lovelace");

  assertThrows(IllegalArgumentException.class,
      () -> name.setLastName(""));
}
```

---

## 9. Testidéer

### Gyldige input
- ændring fra ét navn til et andet

### Grænsetilfælde
- korte navne
- samme navn igen

### Ugyldige input
- null
- tom streng

---

## 10. Designprincip

> Objektet er ansvarligt for sin egen gyldighed – hele tiden.

Det betyder:
- både konstruktør og metoder skal validere
- ingen metode må efterlade objektet i en ugyldig tilstand

---

## 11. Refleksionsspørgsmål

1. Hvornår giver det mening at ændre et objekt?
2. Hvad er forskellen på konstruktør og mutator?
3. Hvordan sikrer vi invarianten i alle metoder?
4. Skal Name være mutable eller immutable?

---

## Afslutning

Vi har nu:

- introduceret metoder der ændrer state
- set hvordan invariant stadig skal beskyttes
- arbejdet med tests for både ændringer og fejl

Dette udvider objektmodellen:

Et objekt har ikke kun data og adfærd –  
det har også en livscyklus, hvor tilstanden kan ændre sig på en kontrolleret måde.
