# Kapitel 4 – Metoder og ansvar

## 1. Introduktion

I de første kapitler har vi arbejdet med:

- objekter som modeller
- state (data)
- invariants (regler)
- validering i konstruktøren

Nu udvider vi vores fokus:

👉 Hvad kan et objekt gøre?

Det handler om **metoder og ansvar**.

---

## 2. Fra data til adfærd

Indtil nu har vi haft simple metoder som:

```java
public String getFullName()
{
  return firstName + " " + lastName;
}
```

Men metoder er mere end “gettere”.

Metoder er den måde, objektet:
- udfører arbejde
- beskytter sin tilstand
- opfylder sit ansvar

---

## 3. Hvad er en god metode?

En god metode:

- hører naturligt til objektet
- arbejder på objektets state
- overholder klassens invariant
- er let at teste

---

## 4. Eksempel: udvidelse af Name

Vi kan udvide klassen med flere metoder:

```java
public String getInitials()
{
  return "" + firstName.charAt(0) + lastName.charAt(0);
}
```

Her bruger vi objektets state til at udlede ny information.

---

## 5. Ansvar

Et centralt spørgsmål i objektorienteret design er:

> Hvem har ansvaret?

Eksempel:

Skal `getInitials()` ligge i:
- Name?
- en anden klasse?

Svar: Name.

👉 Fordi initialer er en naturlig del af begrebet “navn”.

---

## 6. Dårligt design

Eksempel på dårligt design:

```java
public class NameUtil
{
  public static String getInitials(Name name)
  {
    return "" + name.getFirstName().charAt(0)
             + name.getLastName().charAt(0);
  }
}
```

Problemer:
- adfærd ligger uden for objektet
- objektet mister ansvar
- designet bliver spredt

---

## 7. Metoder og invariant

Metoder må ikke bryde invariant.

Hvis vi senere tilføjer metoder, der ændrer state, skal vi sikre:

- at objektet stadig er gyldigt bagefter

---

## 8. Test af metoder

Metoder skal kunne testes systematisk.

Eksempel:

```java
@Test
void getInitials_returnsCorrectInitials()
{
  Name name = new Name("Ada", "Lovelace");
  assertEquals("AL", name.getInitials());
}
```

---

## 9. Testidéer

### Normale tilfælde
- "Ada", "Lovelace" → "AL"

### Grænsetilfælde
- ét bogstav
- små/store bogstaver

### Ugyldige situationer
- (bør allerede være håndteret i konstruktøren)

---

## 10. Designprincip

En vigtig regel:

> Adfærd skal placeres der, hvor data er.

Det betyder:
- vi undgår “utility-klasser”
- vi samler ansvar i objektet
- vi får mere sammenhængende design

---

## Afslutning

Vi har nu arbejdet med:

- metoder som adfærd
- ansvar i objektet
- placering af logik
- test af metoder

Dette er et vigtigt skridt:

Vi bevæger os fra “data + regler” til **aktive objekter med ansvar**.

Det er denne tankegang, der gør det muligt senere at:
- designe større systemer
- skrive gode tests
- bruge værktøjer som Spec2JUnit meningsfuldt
