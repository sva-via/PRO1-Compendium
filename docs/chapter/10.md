# Chapter 10 – Associations

## 1. Introduction

Session 10 introduces relationships between objects.

Until now, most examples focused on individual objects.

Session 10 focuses on how objects collaborate.

The focus is on:

- associations
- aggregation
- composition
- navigability
- multiplicity
- object collaboration
- UML relationships

Object-oriented programming is largely about designing meaningful collaborations between objects.

---

## 2. Objects Collaborate

Objects rarely exist in isolation.

Examples:

- a `Person` may own a `Car`
- a `Student` belongs to a `Class`
- a `House` contains `Room` objects
- a `Library` stores `Book` objects

Relationships between objects are central to domain modelling.

---

## 3. Associations

An association is a relationship between objects.

Example:

```java
public class Person
{
  private Car car;
}
```

A `Person` object is associated with a `Car` object.

The field stores a reference to another object.

---

## 4. Navigability

Navigability describes which object knows about the other.

Example:

```java
public class Person
{
  private Car car;
}
```

The `Person` can navigate to the `Car`.

But if `Car` does not store a `Person` reference, the relationship is one-way.

Example:

![Person → Car](images/association1.jpg)


```text
Person → Car
```

---

## 5. Bidirectional Associations

Sometimes both objects know about each other.

Example:

```java
public class Person
{
  private Car car;
}
```

```java
public class Car
{
  private Person owner;
}
```

Now both objects can navigate to the other.

Example:

```text
Person ↔ Car
```

Bidirectional relationships require careful design.

---

## 6. Multiplicity

Multiplicity describes how many objects participate in a relationship.

Examples:

| Multiplicity | Meaning |
|---|---|
| `1` | exactly one |
| `0..1` | zero or one |
| `*` | many |
| `0..*` | zero or more |
| `1..*` | one or more |

Example:

```text
Person 1 ----- 0..1 Car
```

A person may own zero or one car.

---

## 7. One-to-Many Relationships

Collections are often used in one-to-many relationships.

Example:

```java
public class SchoolClass
{
  private ArrayList<Student> students;
}
```

One `SchoolClass` object may contain many students.

---

## 8. Managing Relationships

The responsible class should manage the relationship.

Example:

```java
public void addStudent(Student student)
{
  students.add(student);
}
```

The collection should usually remain private.

Other classes should not manipulate the collection directly.

---

## 9. Searching Associated Objects

Relationships are often traversed using loops.

Example:

```java
public Student findStudent(String name)
{
  for (Student student : students)
  {
    if (student.getName().equals(name))
    {
      return student;
    }
  }

  return null;
}
```

Objects collaborate through their associations.

---

## 10. Aggregation

Aggregation represents a whole-part relationship.

Example:

```text
Car ◇---- Wheel
```

The parts may exist independently of the whole. 

Example:

- a `Wheel` may exist without a `Car`

The Wheel is part of the Car. You can remove the Wheel and put in storage or reuse it in another car.

Aggregation usually represents weaker ownership.

---

## 11. Composition

Composition is a stronger whole-part relationship.

Example:

```text
House ◆---- Room
```

The part belongs strongly to the whole.

Example:

- a `Room` usually does not exist independently of a `House`

The Room is part of the House, but you cannot remove the Room from the Hourse.

Composition often implies:

- ownership
- lifetime dependency

---

## 12. Comparing Association Types

### Association

General relationship.

Example:

```text
Person ----- Car
```

### Aggregation

Weak whole-part relationship.

Example:

```text
Car ◇---- Wheel
```

### Composition

Strong ownership relationship.

Example:

```text
House ◆---- Room
```

The choice depends on the domain meaning.

---

## 13. UML Relationships

UML diagrams represent relationships visually.

Example:

```text
+----------------+
| SchoolClass    |
+----------------+
| - students     |
+----------------+
```

Relationship lines describe:

- navigability
- multiplicity
- association type

UML helps model object collaboration before implementation.

---

## 14. Constructor Responsibility

Constructors often initialize relationships.

Example:

```java
public SchoolClass()
{
  private ArrayList<Student> students;

  public SchoolClass()
  {
    students = new ArrayList<>();
  }
}
```

Collections should usually be initialized in the constructor.

---

## 15. Responsibility and Associations

The class responsible for the relationship should manage it.

Example:

Good:

```java
schoolClass.addStudent(student)
```

Less good:

```java
schoolClass.getStudents().add(student)
```

Encapsulation still applies.

The internal structure should remain protected.

---

## 16. Removing Associated Objects

Associations often support removal.

Example:

```java
public void removeStudent(Student student)
{
  students.remove(student);
}
```

The responsible class controls modifications.

---

## 17. Null Relationships

Associations may be optional.

Example:

```java
private Car car;
```

A person may not own a car.

Example:

```java
car == null
```

Selection structures are often used to handle optional relationships.

---

## 18. toString() and Relationships

`toString()` methods may include associated objects.

Example:

```java
public String toString()
{
  return name + ", owner=" + owner.getName();
}
```

Care must be taken with cyclic references.

---

## 19. Testing Relationships

Relationships should be tested carefully.

Example:

```java
@Test void addStudent()
{
  SchoolClass c = new SchoolClass();
  Student s = new Student("Bob");

  c.addStudent(s);

  assertEquals(1, c.getNumberOfStudents());
}
```

Tests should verify:

- adding relationships
- removing relationships
- searching
- multiplicity behavior

---

## 20. Typical Beginner Mistakes

Common mistakes:

1. Exposing collections directly
2. Forgetting to initialize collections
3. Placing relationship logic in the wrong class
4. Confusing aggregation and composition
5. Forgetting multiplicity constraints
6. Creating inconsistent bidirectional relationships
7. Forgetting `null` cases
